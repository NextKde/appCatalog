# Maintaining and publishing a catalog

[简体中文](MAINTAINING.zh-CN.md) · [Português (Brasil)](MAINTAINING.pt-BR.md)

Submission PRs run structural validation on a GitHub-hosted VM. They do not run submitted apps, download their installers or receive signing secrets. Structural checks are not a security review.

Before merging, review repository ownership, app ID and existing-ID conflicts, stable Release assets, Flatpak permissions, runtime/extension availability, SHA-256 and optional publisher identity. Test installation and update in a disposable VM. Do not accept scripts or arbitrary download URLs in entries. Translation-only changes must not change app identity or trust.

## First publication

1. Create the GitHub environment `catalog-release` and configure maintainer reviewers and main-branch restrictions.
2. Set environment secret `CATALOG_SIGNING_PRIVATE_KEY` to the ASCII-armored private signing key. If needed set `CATALOG_SIGNING_PASSPHRASE`. Never commit or paste private keys into issues, PRs or logs.
3. Confirm that its public key matches `catalog-public.gpg` and the full primary fingerprint in `catalog-fingerprint.txt`, and the public key pinned by the client. The official seed currently uses the existing NextKde release key. Generating a different key does not make existing clients trust it.
4. Run **Publish catalog** on `main` with a positive integer sequence greater than every previous catalog release. The workflow assembles the JSON, signs its exact bytes, verifies against the pinned public key and uploads `catalog.json` and `catalog.json.sig` in `catalog-N`.
5. Refresh a development client in a VM. Check the source sequence, expiry, app visibility and installation plan before announcing availability.

The default lifetime is 30 days. Publish a new, higher sequence before expiry even if no entries changed. Expired data cannot authorize installs or updates. Never edit or reuse a published sequence, delete history to reset the counter, or format the JSON after signing. A correction is another higher sequence. Release availability does not prove client acceptance.

## Third-party repository setup

Copy the format/tooling, replace the public key and fingerprint with your own, and change `--source-id nextkde` in the publish workflow to a unique identifier matching what users add. Do not reuse the official source ID. Configure your own release environment and secrets. The first release must be a stable GitHub Release with the two fixed asset names above. Users explicitly establish trust in your key; no automatic trust follows from hosting on GitHub.

Root-key rotation is not automatic. A third-party replacement key requires a new source ID and explicit trust; official key changes require coordinated client distribution. Keep the old signing key available until a reviewed transition exists.

## Development commands — VM only

```sh
python3 build_catalog.py --check
python3 -m unittest discover -s tests
python3 build_catalog.py --sequence 1
```

For manual publication, sign the exact generated bytes with the authorized key using SHA-256 or stronger, then verify using `gpgv --keyring ./catalog-public.gpg dist/catalog.json.sig dist/catalog.json`. Prefer the provided workflow, which also enforces increasing published sequence numbers. Never run untrusted app code on the signing runner.

## Keeping the private key offline

The GitHub workflow is optional. A maintainer may assemble and validate in a VM,
copy only `catalog.json` to the signing machine, sign with the existing authorized
key, then return only the JSON and detached signature to the VM for verification.
The private key stays on the signing machine; it need not be exported into GitHub
Secrets. Publish the verified pair in a new stable `catalog-N` Release after
checking the full existing Release history for a higher sequence. Use `--target`
with the reviewed catalog repository commit and retain the signing key outside
this checkout. Re-signing changed JSON requires a new unpublished sequence.

Schema 2 catalog publication embeds approved release manifests and immutable repository icons; see [version approval](docs/PinnedReleases.md).
